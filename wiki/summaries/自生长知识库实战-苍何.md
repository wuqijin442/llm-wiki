# 自生长知识库实战（WorkBuddy + Codex + Obsidian）

> 来源素材：`[[raw/articles/2026-09-12-用WorkBuddy-Codex-Obsidian搭建自生长知识库]]`
> 作者：苍何 ｜ 原文发布：2026-08-09 ｜ 实践基础：Karpathy 公开的 LLM wiki 架构

## 核心要点

1. **传统问答范式的根本缺陷**：RAG / 文件上传问答每次都在"从碎片重拼答案"，答完就散，知识零积累；一百次提问 = 一百次重拼。
2. **LLM Wiki 的解法**：让 Agent 长期维护知识库——已有内容补充、新概念建页、**分歧保留来源/时间/适用范围**，不被一段看似完整的总结抹平。
3. **三层架构**：Raw（证据）/ Wiki（理解）/ Schema（规则）。Raw 只读、Wiki 读写、Schema 定义如何归档更新引用与处理冲突。
4. **"自生长"的判据**：AI 处理完资料后，知识库必须留下变化（新概念、新关联，或一个暂时没有答案的问题）。没有变化就不是自生长。
5. **三种搭建路径**：① 直连 Agent（可控但需调 Schema）② Skill 封装（`ingest` / `retrieve` 即用）③ Obsidian 插件（可视化、门槛最低）。
6. **分工原则**：人负责规则设定、结果检查、关键判断；Agent 负责重复、耗时、结构化的维护。自生长 ≠ 完全自动化。

## 详细摘要

### 为什么不是 RAG
RAG、NotebookLM、GPT 文件上传本质同构：上传资料 → 提问时召回片段 → 临时综合。问题不在于"找不到"，而在于**每次都在重建理解，且不留痕迹**。LLM Wiki 把"检索"换成"编译"——理解被一次性沉淀成结构化页面。

### 三层架构与权限
| 层 | 内容 | 规则 |
| --- | --- | --- |
| Raw | 文章、论文、聊天记录 | 只存不改，是证据 |
| Wiki | 概念、实体、主题 | Agent 读写维护 |
| Schema | `AGENTS.md` 一类规则文件 | 定义归档/更新/引用与冲突处理 |

### 为什么选 Obsidian
本地目录 + Markdown 纯文本 → 数据自主、工具可换、知识不搬家；文件形态天然适合 Agent 直接读写；双链/反链/图谱帮助发现核心节点与孤立页面；Git 可留变更记录。它同时是**存储底座、人机界面、知识观察窗口**。

### 三种搭建方法对比
| 方法 | 形态 | 优势 | 代价 |
| --- | --- | --- | --- |
| 直接搭建法 | 自己写 `AGENTS.md` + 提示词 | 完全可控，Schema 可深度定制 | 提示词与工程化门槛高，规则要持续调 |
| Skill 封装法 | `ingest` / `retrieve` 技能 | 省去反复写提示词 | 操作仍在 Agent 侧，缺可视化反馈 |
| Obsidian 插件法 | 插件内完成初始化/入库/检索 | 门槛最低，可视化 | 依赖插件授权与能力 |

### 素材入口
Web Clipper（电脑剪藏 → `raw/articles/`）、ima / WorkBuddy 小程序（手机碎片）、Agent 代收（飞书等散落资料）。

## 个人理解与启发

- **"编译 vs 检索"是这套模式最锋利的表述**：RAG 是把理解成本推到每次提问，LLM Wiki 是把理解成本前移到入库一次，之后复用。这与工程上"预计算/物化视图"的思路完全一致。
- **冲突不许抹平，是知识库可信度的地基**：传统总结会自然地把分歧"和稀泥"，结果是看起来完整、实际上失真。要求保留来源+时间+适用范围，等价于把每页都做成带引用与时效的证据。
- **"每次 ingest 必须留下变化"可判定、可审计**：这条把"自生长"从口号变成了验收标准——看 `wiki/` 有没有 diff 即可，本库已把它写进 `AGENTS.md` §4。
- **三种方法不是三选一，而是递进**：先用直连法把结构跑通 → 用 Skill 固化流程 → 需要界面化时上插件。本库当前正好走在这条路上（直连 + 自带 `skills/llm-wiki/SKILL.md`）。
- **本文的边界（后续素材补充，2026-07-28）**：本文所述的自生长只覆盖了**编译环**——它证明"库在长"，却未证明"人在长"。同主题的 [[双环知识飞轮-摘要]] 指出：写库的是 AI，人的大脑未必有任何变化；补完这半圈还需要再开一条「互动通道 + 回流带」。两篇合看才构成完整判断。
